# Trade benchmark baseline — 17 September 2026

The first measured Avrogen baseline removes much of avro2s's overhead for this
schema. Native Avrogen reads are approximately level with default generated Java
Avro at 32 and 1,024 integer elements. Native writes beat that default Java path,
but Java's generated custom writer is faster for the larger collection.
This is one matching-schema datum workload, not a general ranking of the libraries.

## Representative result: 32 integer elements

Times are nanoseconds per record, mean ± JMH's reported 99.9% confidence interval
half-width. Allocations are bytes per record. Lower is better.

| Implementation | Read ns/op | Write ns/op | Read B/op | Write B/op |
| --- | ---: | ---: | ---: | ---: |
| avro2s | 544.5 ± 53.6 | 768.3 ± 186.7 | 2,600 | 1,768 |
| Java specific, default fast reader | 226.9 ± 3.1 | 252.5 ± 3.8 | 1,016 | 112 |
| Java generated custom coders | 605.3 ± 62.4 | 138.3 ± 34.5 | 992 | 64 |
| Avrogen + native binary runtime | 226.1 ± 5.9 | 136.9 ± 9.9 | 960 | ≈0 |
| Avrogen + Java binary primitives | 244.5 ± 10.3 | 113.5 ± 15.9 | 1,088 | 64 |
| Java generic | 243.7 ± 8.1 | 255.2 ± 17.9 | 1,032 | 108 |

The native write result is below one allocated byte per operation in the GC
profiler; it is displayed as ≈0. This applies to a warmed, reused output buffer,
with input data constructed outside timing and no final byte-array copy. It is
not a claim that end-to-end serialization or the library allocates nothing.

## What the measurements support

- **avro2s versus default Java:** with 32 elements, avro2s takes 2.4× the read time
  and 3.0× the write time. It allocates 2.6× as many bytes on reads and 15.8× on
  writes. At 1,024 elements, the time ratios are 3.4× for reads and 2.8× for writes.
- **Avrogen versus avro2s:** avro2s takes about 2.4× as long to read and
  5.6× as long to write as native Avrogen at 32 elements. At 1,024 elements those ratios are 3.4× and
  3.9×. The generated avro2s class visibly converts its Scala collection through
  Java-compatible collections in `get` and `put`; the allocation results support
  making that conversion path a priority. The benchmark does not isolate every
  individual cause of the difference.
- **Avrogen versus default Java:** native read means are effectively the same at
  32 elements (226 versus 227 ns) and 1,024 elements (4,830 versus 4,823 ns); their
  confidence intervals overlap. Native writes take about 46% less time at 32
  elements and 27% less at 1,024. Native read allocation is slightly lower at 32
  elements, but slightly higher at 1,024, so it does not universally allocate less.
- **The generated codec already helps with Java primitives:** Avrogen with the
  Java binary adapter reads/writes the 32-element value in 245/113 ns. Direct
  Scala codecs are useful even before replacing the binary engine. That gain
  includes the different generated model and collection representation.
- **The native binary engine is not uniformly faster:** at 1,024 elements,
  Avrogen writes in 4,677 ns with the native engine versus 3,899 ns with Java
  primitives. Java's generated custom writer takes 3,427 ns. Native validation
  and output buffering differ as well as primitive implementation. Measure those
  costs separately before choosing an optimization.
- **Custom Java decoding is a separate configuration:** Avro 1.12.1's default
  fast reader bypasses generated `customDecode`. The custom baseline disables
  that reader and is slower on this schema. The ordinary Java and avro2s baselines
  keep the fast reader enabled; neither is artificially restricted to the slower
  custom-decoding configuration.

These ratios divide measured means; they are not confidence intervals for ratios.
The empty-collection avro2s write and Java custom cases have particularly wide
intervals. Avoid precise rankings from their means. Use a quieter machine and more
forks before publishing strong claims, and broaden the schema set before making
library-wide decisions.

## Scope and reproducibility

The record has `long`, `string`, `double`, and `array<int>` fields, with collection
sizes 0, 32, and 1,024. The string is `AVRO-λ`; integer elements are outside the
default JVM small-integer cache. All methods use the same raw datum layout and
values. Namespaces differ only to allow all generated classes to coexist.

Java's default generated models return `Utf8` through `CharSequence` and Java
collections. avro2s returns `String` and `List[Int]`; Avrogen returns `String` and
`Vector[Int]`. Java therefore defers Unicode string materialization. Native input
also validates UTF-8 and enforces decode limits. These are measurements of the
normal returned models and configured validation, not identical work at every
layer. All collection representations retain boxed integer elements.

Writers reuse buffers/encoders. Readers allocate fresh decoder/input objects and
fresh results; datum readers and their cached schema machinery are reused.
Mutable result reuse, cold schema setup, evolution, files, compression, registry
calls, and application-level latency are outside this benchmark.

- Apple M1 Pro, 16 GiB RAM, macOS 15.4, aarch64.
- Amazon Corretto 21.0.0.35.1 (`21+35-LTS`), fixed 512 MiB initial/maximum heap.
- Scala 3.3.6, sbt 1.11.0, Apache Avro 1.12.1, JMH 1.37.
- Two forks, one thread, five 1-second warmup iterations and five 1-second
  measurement iterations per fork; GC allocation profiler.
- 36 benchmark cases completed, each with 10 measured iterations across two forks.
- 58 correctness tests passed. These include every one of the six writers against
  all six readers at all three sizes, plus checks that Java custom coding actually
  dispatches to the generated methods. Trial setup repeats the compatibility checks.
- Local developer-machine run; background activity and CPU frequency were not
  isolated. No performance threshold is asserted by the correctness tests.

The comparison classes are actual generated output, with versions, schemas,
options, hashes, and the exact avro2s commit in the
[baseline provenance](../../benchmarks/generator/README.md). Normal tests and
benchmarks need no avro2s checkout, manual JAR extraction, or source-JAR inspection.
Reading the published Avro source JAR was diagnostic research into decoder
selection; the relevant behavior is now checked by the automated test suite.
