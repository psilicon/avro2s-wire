# Native speed follow-up — 17 September 2026

The changes reduce native execution time in **all 13 previously identified weak
read/write cases**, by about **16–77%** against the fresh native baseline. Eight
of those cases now have lower means than the fastest measured Java datum
implementation. This is a result for this fixed corpus and JVM, not a promise
that every schema or input improves. In the full current comparison, native has
lower mean times in **21 of 26** read/write cases against the fastest measured
Java datum implementation. The separate longer small-integer confirmation changes
that one Java/native ranking, so the win count is descriptive of the broad run.

## Comparisons that return actual Strings

Default Java Avro readers retain `Utf8` and Java collections. The additional
`DecodedStringBenchmark` explicitly requests and verifies String fields and map
keys. Scala `String` and `java.lang.String` are the same type; collection and
record representations still differ.

| Read workload | Native | Java generic, String output | Java specific, String output | avro2s |
| --- | ---: | ---: | ---: | ---: |
| ASCII | 54.5 ns | 115.4 ns | 117.1 ns | 114.7 ns |
| Mixed Unicode | 2.444 µs | 2.325 µs | 2.357 µs | 2.300 µs |
| Populated arrays/map | 8.264 µs | 7.205 µs | 7.126 µs | 15.703 µs |

Native is about 5% behind the fastest String-returning Java reader for mixed
Unicode and 16% behind for the populated collection record. The same generated
Scala model on Java primitives takes 10.147 µs for that collection read, compared
with native's 8.264 µs. These controls distinguish representations and complete
implementations; they do not isolate a single source of overhead.

Native Unicode reading allocates **11,144 B/op**, versus **14,072 B/op** for
Java-specific String output and avro2s. The much smaller default Java allocation
retains UTF-8 bytes without constructing the same decoded String.

The measured Corretto 21 String constructor allocates a Latin-1 candidate array,
a UTF-16 working array and a trimmed final array for this mixed text. Their
payload sizes are 2,816, 5,632 and 2,560 bytes; including array headers/alignment,
they account for 11,056 allocated bytes. This source-derived accounting is
consistent with the GC totals, rather than an allocation-stack profile. Only
the final backing array is retained by the String. Removing the preliminary
validation scan improves time without removing those JDK temporary arrays.

## Remaining gaps and tradeoffs

The strongest Java datum mean still wins five main operation cases: small-int
array writing, ASCII writing, mixed-Unicode reading/writing and populated
collection reading. The last two read comparisons include the default Utf8
representation; the equivalent-String results above are more informative about
the cost of text materialization. Native strict validation and immutable
collections remain enabled.

The Java custom small-int writer has an unstable ranking across runs, despite
unchanged Java model source. The main run measures 1.074 ± 0.026 µs for Java
versus 1.623 ± 0.023 µs for native. A separate longer two-fork confirmation
(5 × 1 s warmup and 5 × 1 s measurement) measures Java at 1.806 ± 0.045 µs and
native at 1.630 ± 0.035 µs, reversing the ranking. The original historical Java
mean was 1.821 µs. All runs remain separately reported; we do not select the
favorable one or claim a stable winner for this case. The measurements do not
establish the cause of the Java variation.

The full tables also retain the higher bytes-write mean (79.5 → 90.0 ns,
with overlapping intervals) and the logical-write allocation increase
(80 → 112 B/op). Native still beats Java in both cases; neither is hidden by
focusing only on the original deficits.

Longer string writing now uses JDK UTF-8 conversion and therefore allocates
temporary arrays: 1,040 B/op for the main ASCII string and 6,688 B/op for mixed
Unicode. The old native writers allocated almost nothing in those reused-buffer
cases. This is a deliberate throughput/allocation tradeoff; tiny strings retain
the direct encoder because it performed better for small fields and map entries.

There is a confirmed **emoji-only writing regression**. At 4,096 code points,
the old writer takes 8.724 ± 0.130 µs and the retained writer 9.478 ± 0.099 µs,
about 8.6% longer, allocating about 40,992 B/op instead of almost zero. At
32 code points, 81.4 ns becomes 85.5 ns, about 5% longer, with 352 B/op.
Both use matched two-fork timing for this confirmation. Literal U+FFFD reads
remain approximately unchanged because they need the strict validation fallback.

An alternative direct encoder for supplementary-led strings removed allocation
but slowed the mixed supplementary/ASCII/CJK cases by 50–115% in its paired
pilot. It was rejected. A wider sentinel scanner and blanket iterator traversal
were also rejected after measurement. Their source patches and raw results remain
available, separately labelled as experiments.

## Allocating APIs and additional checks

The matched 14-case convenience-API runs include fresh input/output wrappers and
`encode`'s returned byte array. Integer encode/decode both improve by about 39%;
populated collection encode improves by 27% and decode by 14%. ASCII-short encode
improves by 25% and decode by 29%. The gains therefore extend beyond reused buffers.

The complete tables also show two measured allocating-encode regressions with
separate intervals: 4,096-byte payloads take 301.3 → 309.4 ns (+2.7%), allocating
8,512 → 8,536 B/op; long emoji strings take 9.836 → 10.304 µs (+4.8%), allocating
33,112 → 74,104 B/op. Empty-collection encode, bytes decode and nested encode
have overlapping before/after intervals. These are native before/after controls,
not additional comparisons with Java datum writers.

The Trade follow-up compares native with the same generated Scala model on Java
primitives at 0, 32 and 1,024 array elements. Native has lower times in all six
read/write pairs. At 1,024 elements, native read is 4.051 µs versus 4.440 µs on
Java primitives; native write is 2.207 µs versus 3.806 µs. The full tables retain
all sizes, allocation and intervals, alongside the separate schema-evolution and
mixed supplementary-text checks. Reused native evolution plans take about
311–316 ns versus Java generic's 365–366 ns across the two payload sizes,
allocating 640 versus 1,840 B/op. Plan construction remains a separate operation
at approximately 23 µs and 130 KB; it should be reused rather than repeated per
record. These resolution readers still return different record/text models.

## Implementation and usage

- One-byte and unrolled wider integer paths reduce repeated bounds checks and
  cursor updates; checked tails retain physical and sized-block boundaries.
  Generated physical int/long arrays use native bulk writers with a local cursor.
- Public JDK little-endian array views accelerate float/double operations. A tiny
  package-private Java helper gives reads primitive invocation
  descriptors, avoiding boxing introduced by the Scala VarHandle call form.
- String reads use JDK decoding and perform the strict byte validation fallback
  when the result contains the decoder's replacement text. Literal replacements
  remain valid. Empty and at-most-16-UTF-16-unit writes have direct paths;
  longer writes validate possible encoder replacements after JDK conversion.
- Map readers select a suitable builder, map writers avoid entry tuples, and UUID
  parsing validates and accumulates canonical ASCII hex in one pass.

Generated models use the existing String, immutable Vector/Map and owned Bytes
types. The native runtime gains no Apache Avro dependency, unsafe access or
private JDK API use. Newly generated int/long-array codecs need the updated
runtime's `writeIntArray`/`writeLongArray` methods. Existing custom outputs inherit
defaults that preserve array and per-item callbacks, including Java's blocking
encoder. Regenerate and use the matching runtime together.

## Validation and measurement

The final candidate passes **171 tests across 26 suites** on JDK 11 and in a clean JDK 21 run, including
the expanded seed-42 campaigns: 197 matching schemas / 2,174 values, 136 evolution
pairs / 928 values, and 119 wire schemas / 476 values. New checks include strict
Unicode oracles, numeric widths/overflow/block boundaries, raw floating bits,
bulk callbacks, map collisions/duplicate keys and buffer ownership. See the
[testing guide](../testing.md) for commands and coverage limits.

Measurements use Apple M1 Pro, macOS 15.4 arm64, Corretto 21.0.0.35.1 / JDK 21+35,
Scala 3.3.6, Avro 1.12.1 and JMH 1.37. Main runs use one thread, two forks, three
500 ms warmups and five 500 ms measurements per fork, a fixed 512 MB heap and
the GC profiler. Jobs run serially. Intervals are JMH's reported 99.9% intervals;
overlap is descriptive, not a formal two-sample test or a speedup confidence
interval. They do not capture every source of machine or JIT variation.

Fresh native baseline source is `59d35ee` plus its recorded harness patch. The
retained implementation is committed in `6e6c0ef`; `5e3f95f` adds only String
profiles and regression tests. The main after run uses `5e3f95f`. Decoded-String
and the original 13 text-profile results retain their `6e6c0ef` attribution;
the production implementation is byte-for-byte identical across these commits.
The original broad String before sweep was a shorter one-fork pilot; the emoji
regression received the separate matched confirmation. Source equivalence and
every campaign's actual protocol are recorded in the provenance artifacts.

These are warmed in-memory records. They do not establish arbitrary-schema
performance, startup, tail latency, I/O, compression, container files, schema
registry traffic or service throughput. Allocation is heap bytes allocated per
operation, including temporary objects, rather than retained or peak memory;
see the [allocation measurement explanation](README.md).

## Reproduce

Use the recorded source commit and a chosen executable JVM. The runner retains
commands, exact parameters, source hashes, raw JSON and logs, and rejects source
changes or missing cases. No manually unpacked dependencies or existing build
output are required.

```sh
sbt test
benchmark_java=/absolute/path/to/java
benchmark_results=/absolute/path/to/new-results
python3 scripts/run-performance.py --java "$benchmark_java" --output "$benchmark_results" --label comparison --profile comparison
python3 scripts/run-performance.py --java "$benchmark_java" --output "$benchmark_results" --label decoded-strings --profile decoded-strings
python3 scripts/run-performance.py --java "$benchmark_java" --output "$benchmark_results" --label strings --profile strings
python3 scripts/run-performance.py --java "$benchmark_java" --output "$benchmark_results" --label api --profile api
```

The [artifact guide](speed-2026-09-17/PROVENANCE.md) explains exact historical
snapshot reconstruction, compressed logs and independent verification. The
raw environment manifests preserve the commands for narrower confirmation runs.
